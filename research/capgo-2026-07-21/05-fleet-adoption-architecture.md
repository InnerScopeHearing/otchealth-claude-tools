## 1. Skill Adoption Matrix

Scope: all 49 skills in the Capgo marketplace (the package.json/README call it "49"; the live capgo.app/skills/ page counts "48," a one-skill discrepancy in Capgo's own materials, most likely `skill-creator` being counted differently between the repo listing and the marketing page. Flagging, not resolving, since it does not change any adoption call) crossed against the 8 apps and the 6 exec agents (CTO, CFO, COO, CRO, CLO, Developer).

**Overlap methodology.** The fleet's `octools` (the live-synced shared toolkit every session pulls from `otchealth-claude-tools`) already ships roughly 25 Capacitor/Ionic-flavored skills from a prior pack, visible in this session's own skill listing: `capacitor`, `capacitor-angular`, `capacitor-app-creation`, `capacitor-app-development`, `capacitor-app-spm-migration`, `capacitor-app-upgrades`, `capacitor-expert`, `capacitor-in-app-purchases`, `capacitor-plugin-development`, `capacitor-plugin-spm-support`, `capacitor-plugin-upgrades`, `capacitor-plugins`, `capacitor-push-notifications`, `capacitor-react`, `capacitor-vue`, `capawesome-cli`, `capawesome-cloud`, `ionic-angular`, `ionic-app-creation`, `ionic-app-development`, `ionic-app-upgrades`, `ionic-appflow-migration`, `ionic-enterprise-sdk-migration`, `ionic-expert`, `ionic-react`, `ionic-vue`. Six of these are **exact name collisions** with Capgo marketplace skills (`capacitor-app-upgrades`, `capacitor-plugin-spm-support`, `capacitor-plugin-upgrades`, `capacitor-plugins`, `capacitor-push-notifications`, `ionic-appflow-migration`, `ionic-enterprise-sdk-migration`, seven actually) and the fleet's own generic `skill-creator` is a name collision with Capgo's `skill-creator` too. Do NOT double-install colliding names as loose top-level skills; where Capgo's version is installed at all, it arrives namespaced under its bundling plugin (e.g. `capacitor-core:capacitor-plugins`), which avoids a hard filename clash but does NOT avoid a **routing** clash: two skills with similar trigger descriptions competing for the same natural-language prompt is a real, unresolved ambiguity risk that this report flags at every collision below rather than silently picking a winner.

**CRITICAL FINDING, read this before anything else in this section.** The octools skill list independently contains `capawesome-cli` and `capawesome-cloud`. Capawesome is not a Capgo product, it is Capgo's direct competitor in the exact same OTA/live-update space, to the point that the Capgo marketplace ships a dedicated `capawesome-live-update-migration` skill whose entire purpose is migrating an app OFF Capawesome and ONTO Capgo. The coexistence of `capawesome-cli`/`capawesome-cloud` skills alongside a fleet-wide Capgo OTA rollout is either (a) harmless historical residue from before the fleet standardized on Capgo, in which case it should be pruned to stop it from ever getting invoked by accident on a fleet app, or (b) evidence that some app or exec-agent workflow is still actually pointed at Capawesome Cloud, in which case that is a live platform-fragmentation bug that should be found and fixed before OTA rollout continues past iHEARtest. This report cannot tell which from the materials available; it is the single highest-priority action item to hand to the CTO before Task #31 proceeds further.

## 2. Plugin Gap Analysis

Existing fleet plugin footprint, confirmed: `@capgo/capacitor-updater` fleet-wide (the OTA engine itself). iHEARtest additionally runs 8 named Capgo plugins: `capacitor-in-app-review`, `keep-awake`, `privacy-screen`, `sheets`, `transitions`, `video-player`, `webview-crash`, `webview-guardian`. No other app's CLAUDE.md or HANDOFF names any `@capgo/*` plugin beyond the shared updater, so the gap below is real, not a duplicate-detection exercise for those 7 apps.

**Supersession finding (from the 03 report, restated as the load-bearing fact for this section):** none of the 58 individually-researched Capgo plugins directly supersede or duplicate iHEARtest's existing 9. The value here is net-new capability, plus two genuine "replace hand-rolled Swift with a maintained plugin" candidates worth a deliberate spike (not an ad-hoc swap): Flatstick's shipped Watch/Widget/Live-Activity native-extension code (`ios/integrate_native_targets.rb`) versus `@capgo/capacitor-watch` and `@capgo/capacitor-widget-kit`/`@capgo/capacitor-live-activities`; and iHEARtest's fragile hand-built iOS Share Extension (documented as a "Known gotcha" in its own CLAUDE.md) versus `@capgo/capacitor-share-target`.

### 3.2 Keeping it updated

The house standard for staying current is the octools live-sync pattern (`setup/octools-sync.sh`, a UserPromptSubmit hook that re-pulls `otchealth-claude-tools` main every session, plus `FLEET-BULLETIN.md` entries announcing fleet-affecting changes). The Capgo marketplace does **not** use that mechanism, it is a Claude Code plugin marketplace, updated via `claude plugin marketplace update capgo-skills` (or equivalent re-add), a fundamentally different update path than a git pull of the fleet's own toolkit.

**Recommendation:** do not try to fold the Capgo marketplace into the octools live-sync git repo. Instead:
1. Add a line to `dream-team/FLEET-TOOLKIT-REFERENCE.md` (the master tool-level index) documenting the Capgo marketplace as an externally-updated source, with its own update cadence.
2. Run `claude plugin marketplace update capgo-skills` on a fixed cadence (monthly is reasonable given the marketplace's own `metadata.json` dates cluster January through May 2026, i.e. it is actively maintained but not weekly-churning), or whenever the CTO notices a version bump in `package.json`'s `"1.1.0"` field.
3. When an update lands, run the same `bulletin.mjs add` announcement pattern the fleet already uses for toolkit changes, so every running agent picks up "Capgo skills updated to vX.Y.Z, changelog: ..." on its next prompt via the existing bulletin-surfacing mechanism, keeping the two update channels (octools git-pull, Capgo marketplace-update) visible through one shared announcement surface even though their underlying mechanics differ.
4. Re-run the collision audit (Section 1's name-collision list) after every Capgo marketplace update, since a version bump could add or rename skills and change the collision surface.

### 3.3 Which plugins go into which repos, as npm deps

Per-repo `package.json` dependency rules already exist and must be honored exactly as written, not reinterpreted for Capgo packages:
- **7-day minimum dependency cooldown** (iHEARtest's CLAUDE.md, explicitly: "New dependencies respect a 7-day minimum cooldown"). Any new `@capgo/*` plugin added to any app repo sits for 7 days before merge, same as any other dependency; do not treat Capgo packages as exempt because they are "just OTA infrastructure."
- **Exact pinning, not ranges.** The fleet already SHA-pins GitHub Actions; the same precision culture should extend to `@capgo/*` npm versions, pin exact (`"@capgo/camera-preview": "1.2.3"`, not `"^1.2.3"`), given several plugins in the catalog showed very low adoption (Mock Location Detector: 3 GitHub stars; Background Geolocation: 0 monthly downloads at fetch time), meaning a caret-range auto-upgrade on a low-maturity package carries real risk.
- **package-lock.json (or the app's equivalent lockfile) stays committed** and any Guardian/dependency-review process already in place for each repo reviews the full lockfile delta for `@capgo/*` additions exactly as it would for any other dependency.
- `npx @capgo/cli@latest` (never a global install, never bare `capgo`) is the fleet's standardized invocation form for CLI operations, per the marketplace's own internal inconsistency flagged in report 01 (section 30's note that `capgo-live-updates`'s SKILL.md uses the bare `capgo` form while every other Capgo skill recommends `npx @capgo/cli@latest`). Standardize on the latter everywhere, including CI.

## 4. Ops Integration

### 4.1 Capgo channel strategy mapped onto the Mark-review ritual

iHEARtest's Mark Moore review ritual (per its CLAUDE.md: `qa/build-review-X.Y.Z.html`, rendered PDF, his completed scan returns to `qa/mark-reviews/X.Y.Z/`, no external-tester rollout without his SHIP-IT) is a **native-binary** gate, it reviews a TestFlight build, not a JS bundle. Capgo's channel model maps onto it as a complementary, faster inner loop, not a replacement:

- Give Mark's review cohort its own Capgo channel (e.g. `mark-review`), device-pinned via the Devices API's cloud-override mechanism (`POST /device/`, the #2-priority tier in Capgo's channel-assignment precedence) or via `CapacitorUpdater.setChannel({channel:'mark-review'})` if self-assignment is enabled on that channel. This lets JS/HTML/CSS-only fixes Mark flags mid-review reach his device in minutes, without waiting for a new Depot build and a new TestFlight upload, **as long as the fix is genuinely web-layer-only** (per Section 1's restated hard constraint: native code, entitlements, permissions, icons, and store metadata never ship via OTA).
- The 75-tester external-rollout gate stays exactly as documented (no rollout without Mark's SHIP-IT), and should map onto Capgo's staged **percentage rollout** (`--rollout-percentage`, 10% -> 50% -> 100%, with `--auto-pause-*` as an automatic circuit breaker on a bad rollout) for the OTA layer specifically, once a build has cleared Mark's review and entered the tester pool. This gives the fleet two independent staging mechanisms that should be used together, not confused: TestFlight's own phased native rollout for binary changes, Capgo's percentage rollout for OTA bundle changes layered on top of an already-approved binary.
- Every OTA bundle pushed to a channel that any external tester or Mark himself is on should be tagged/logged the same way the fleet already tags native builds (`tf/<marketingVersion>+<CFBundleVersion>`), so there is a durable record of exactly which JS bundle a given tester saw at a given moment. This does not exist as a convention yet and should be added as a lightweight rule (e.g. a git tag or a line in `qa/RELEASE-LEDGER.md` per bundle push) rather than left implicit.

### 4.2 Capgo channel strategy mapped onto the Depot native-build cadence

- **The channel default should reset on every native build**, not accumulate. Per Capgo's own device-assignment precedence, `resetWhenUpdate` (default true) already clears downloaded OTA bundles when the native app itself updates via the store, since a native update supersedes any pending OTA bundle. Confirm this default is left ON everywhere (it is not something any fleet app's docs currently call out explicitly, worth adding to each app's CLAUDE.md OTA section).
- **Every Depot dispatch that touches native code should be paired with an explicit decision about the OTA channel's `defaultChannel` bundle**, since a stale OTA bundle sitting on top of a brand-new native binary (if compatibility checking is skipped) is exactly the kind of drift `bundle compatibility` and `--fail-on-incompatible` exist to catch. Recommend wiring `bundle compatibility` as a pre-upload check in whatever process pushes OTA bundles, not just relying on manual discipline.
- **The 10-second `notifyAppReady()` boot-timing constraint should be explicitly verified against each app's actual cold-boot sequence as part of that app's OTA-wiring task under #31**, not assumed. Companion (Firebase Auth state on boot) and any future MedReview mobile wrap are the two most likely candidates for a slow-enough boot path to risk tripping Capgo's rollback-on-timeout; this is a concrete, checkable item to add to each app's remaining #31 work, not a theoretical risk.

### 4.3 Telemetry into the CTO/COO dashboards

Capgo's Statistics API (`api.capgo.app/statistics/...`) gives four endpoints directly useful for fleet dashboards, none of which appear to be wired into anything today:

- `GET /statistics/org/:org_id/` with `breakdown=true` gives a single call that returns MAU/storage/bandwidth for every app under the "OTCHealth Inc." Capgo org, the natural per-app rollup for a **COO Morning Briefing**-style scan (the fleet already runs a 7am scheduled briefing pattern for other signals per `otchealth-cto/CLAUDE.md`'s Hyperagent daily-ops section; this is a same-shaped addition, not a new pattern).
- `GET /statistics/app/:app_id/bundle_usage` returns a chart-ready time series of what percentage of active devices sit on each bundle version, exactly the tool for verifying a staged rollout's actual adoption curve rather than assuming the dashboard's percentage setting reflects reality. Feed this into whatever surface currently tracks build/version status per app (the CTO's per-app `cto-bridge/STATUS.md` pattern, or `qa/RELEASE-LEDGER.md`, are both plausible homes; recommend the release ledger since it already exists as a per-build row structure and bundle adoption is conceptually a build-adjacent fact).
- MAU is explicitly a **device** metric, not a human-user metric ("A distinct device that contacts Capgo during a rolling 30-day period"), a real distinction to carry into any CFO/CRO-facing usage reporting that might otherwise conflate Capgo MAU with actual subscriber or user counts from RevenueCat/PostHog.
- The `Devices` API's 90-day retention and `country_code` field is a low-cost geographic-distribution signal (Cloudflare-derived, no PII) that could feed a COO or Growth-agent dashboard without touching any PHI or PII surface, worth flagging as an easy add once the basic MAU/bundle-adoption wiring exists.

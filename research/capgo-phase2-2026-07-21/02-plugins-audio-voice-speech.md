# Slice: Audio / Voice / Speech Plugins (native-audio, speech-recognition, speech-synthesis, TTS, audio-session)

Source: otchealth-claude-tools/research/capgo-2026-07-21/03-capgo-plugins-web.md (150-plugin catalog) and 04-capgo-cloud-docs.md (platform docs).
Cross-referenced fleet CLAUDE.md files: iHEARtest, AWARE, aware-aural-rehab-ci, OTCHealth Companion, InnerEase, Flatstick, FourVault, MedReview, otchealth-claude-tools.

Scope of this slice: every plugin in the catalog that touches audio playback, audio session/routing, speech recognition (STT), speech synthesis (TTS), voice calling/VoIP, and adjacent media-session/lock-screen-audio controls. I also pull in the Communication-category voice plugins (Twilio Voice, Twilio Video, Incoming Call Kit, RealtimeKit) because the focus hint explicitly calls out the Twilio/ElevenLabs voice-agent fleet, and I pull in Mute (silent-switch detection) and Volume Buttons because they are audio-adjacent device signals that directly affect audio UX correctness.

No em dashes or en dashes used anywhere below.

## 1. Speech Recognition (`@capgo/capacitor-speech-recognition`)

iOS, Android. Methods: `available()`, `isOnDeviceRecognitionAvailable()` (locale-dependent), `start()`, `stop()`. Streaming partial results, cross-platform parity.

- **Companion (Pillar 1, voice assistant; non-negotiable rule 4, "every action must also be reachable by voice"):** direct hit. Companion's architecture is Vertex Gemini Live for the heavy conversational AI, which is a HARD-CAPPED usage dimension per its own pricing/usage-caps rules (Gemini Live minutes hard-capped server side in `usage-caps.ts`). A lightweight on-device wake-word or short command layer via this plugin ("Hey, read this to me," "call my daughter," "what is this pill") can handle the simple, high-frequency voice actions WITHOUT opening a Gemini Live session, only escalating to the expensive cloud session for genuinely open-ended visual+voice queries. This is a direct unit-economics lever on a hard-capped, metered, revenue-gating resource. Call: adopt-now. Effort: M (wiring plus a command-intent router plus a fallback path when on-device recognition is unavailable for the user's locale).
- **AWARE (12-tile training grid, senior 50-75 accessibility posture):** voice navigation of the tile grid ("start lesson three," "repeat") matches AWARE's senior-first accessibility requirement (1.5x text scale, high contrast, axe-core gate) extended into the audio modality, which none of AWARE's current wiring (Sentry only, no PostHog yet) currently touches. Call: adopt-later (after core roadmap items land). Effort: M.
- **InnerEase (senior-adjacent 50-75, on-device-first non-negotiable rule 5, "no backend, no PHI, no BAA in V1"):** voice-driven exercise navigation is architecturally the RIGHT fit here specifically because the recognition itself needs to happen without a backend call if InnerEase is to honor its own on-device-first rule. Pair with the on-device LLM plugin (see item 8) for a fully local voice loop. Call: adopt-later (InnerEase is pre-code / Phase 0 not yet landed). Effort: M once Phase 0 fork lands.
- **MedReview, HARD COMPLIANCE FLAG:** MedReview's phased plan puts a Capacitor wrap at V1.1/V1.2. Before this plugin (or any STT) ever touches a medication-name, symptom, or dosage utterance, the underlying platform speech engine must be verified as either fully on-device (`isOnDeviceRecognitionAvailable()` true and enforced) or, if it phones home to Apple/Google's cloud speech servers, that path is OUTSIDE the GCP BAA ring entirely (same class of gap already flagged for the Health plugin in the main report: "no PHI/privacy documentation surfaced, flag before wiring to a PHI-adjacent surface"). This is a real anti-pattern trap: adopting this plugin naively on a future MedReview Capacitor build would silently send PHI-adjacent speech audio to a non-BAA vendor cloud. Call: skip until on-device-only mode is confirmed and enforced; spike to verify before any MedReview mobile use. Effort: S (verification spike).
- **Fictionary:** if a future voice-gameplay mode is added (word-guessing, charades-style), this is the plugin. No current CLAUDE.md detail confirms this is planned; flagged as catalog-level only. Call: skip for now (no confirmed feature).

## 2. Speech Synthesis (`@capgo/capacitor-speech-synthesis`)

iOS, Android, Web (notably Web IS supported here, unlike most Media-category plugins). Methods: `speak`, `synthesizeToFile` (iOS/Android only, not Web), `cancel`, `pause`. 2.6k monthly downloads.

- **InnerEase (on-device-first, no backend in V1):** this is the single strongest architectural match in the whole slice. InnerEase's non-negotiable rule 5 requires no backend and no cloud dependency in V1; on-device OS-native TTS for exercise prompts and relief-session narration satisfies that constraint with zero cloud cost and zero latency, where a cloud TTS call would directly violate the rule. Call: adopt-now (the moment Phase 0 fork lands and the app tree exists). Effort: S.
- **Companion (default TTS is Google Cloud TTS Chirp 3 HD under the GCP BAA; ElevenLabs for the consented voice-clone premium tier):** this plugin is a THIRD, on-device fallback path, not a replacement for either cloud path (BAA coverage and voice-clone identity cannot come from a generic OS voice). The concrete win: when the cloud TTS round-trip is slow or fails (a real risk for a 70+ user on unreliable home wifi, exactly Companion's threat model), an instant on-device "speaking placeholder" prevents dead air, which matters disproportionately for a senior user who may assume the app is broken. Call: adopt-now as a resilience fallback, not primary. Effort: S.
- **AWARE (aural rehab coach narration):** same fallback-narrator logic as Companion; also a candidate PRIMARY narrator for low-stakes UI copy (button labels, confirmations) to avoid burning any future cloud TTS budget on trivial strings. Call: adopt-later. Effort: S.
- **MedReview:** the catalog explicitly notes Web platform support, which is unusual for this category. MedReview V1 IS web-only (Shopify-embedded React SPA, no Capacitor at all in V1 per its phased-delivery plan). Importing a Capacitor plugin purely for its web shim just to get `window.speechSynthesis`-style TTS is unnecessary overhead versus calling the standard Web Speech API directly, since MedReview V1 has no Capacitor runtime to plug into. Call: skip for V1 (use the native browser Speech Synthesis API directly, no Capacitor dependency needed); reconsider this specific plugin at V1.1 Capacitor wrap for parity with the rest of the fleet's plugin choices. Effort: S either way, this is a build-vs-buy note not a blocker.

## 3. Audio Session (`@capgo/capacitor-audiosession`)

iOS ONLY. Methods: `currentOutputs()`, `overrideOutput()`. Scope: AVAudioSession routing/output query and override only, does not itself handle playback.

- **Companion (Known Gotchas, `AmplifyAudioPlugin.swift`):** Companion's own CLAUDE.md documents a hand-rolled native Swift plugin that sets `.playAndRecord` / `.measurement` mode BEFORE `getUserMedia`, specifically to stop WKWebView's default `.soloAmbient` mode from mis-routing Bluetooth audio and fighting the custom EQ. This Capgo plugin's documented API surface (query current outputs, override output) is THINNER than what Companion's bespoke plugin already does (full category/mode configuration). It is not a drop-in replacement as-is. Call: spike only, read the plugin's full native source (not just the fetched doc excerpt) to see if it exposes category/mode configuration beyond the two methods surfaced in the docs; if yes, it could absorb some of the bespoke Swift maintenance burden. Effort: S (spike), M if it turns into an actual migration.
- **iHEARtest and AWARE (both hearing-focused, both explicitly flag AVAudioSession/AirPods routing as "device-only bugs, testable only via TestFlight" in their CLAUDE.md files):** same logic as Companion. A shared, maintained AVAudioSession plugin used consistently across all three hearing/audio-heavy apps would mean ONE place to fix routing bugs instead of three bespoke implementations (or three copies of the same undocumented tribal knowledge). This is a factory-throughput argument as much as a feature argument: less bespoke Swift per app, more shared surface. Call: spike, same as Companion. Effort: S.
- **Flatstick, FourVault, Fictionary, PlantID:** no current audio-routing pain point documented; not relevant.

## 4. Native Audio (`@capgo/capacitor-native-audio`)

iOS, Android. Methods: `configure()`, `preload()`, `playOnce()` (with `deleteAfterPlay`/`autoPlay`), `isPreloaded()`, `stop()`. Framed for short, low-latency SFX, not long-form narration or streaming.

- **Fleet-wide (all 8 apps):** every app currently hand-rolls (or has no standard for) short UI feedback sounds: success chimes, error tones, notification dings. Standardizing on one low-latency SFX plugin fleet-wide is a cheap, low-risk factory-throughput win: one shared pattern in the app-template/scaffolder instead of eight bespoke `<audio>` tag or Web Audio implementations, each with its own latency/preload quirks. Call: adopt-now, fleet-wide, via the app-template/scaffolder so every NEW app gets it by default. Effort: S.
- **AWARE / InnerEase (training exercise cues, relief-session cues):** short cue sounds (correct-answer chime, session-start tone, breathing-pace tick) are exactly this plugin's use case, distinct from the longer narration handled by Speech Synthesis (item 2) or cloud TTS.
- **iHEARtest:** already has the closest-adjacent plugin (`video-player`) but no dedicated SFX plugin; a short "test complete" chime is a natural fit.

## 5. Media Session (`@capgo/capacitor-media-session`, catalog-only, not individually deep-dived in the raw report but description is explicit: "Control media playback from lock screen and notification center")

- **InnerEase (relief-sound sessions, native audio path required per its own CLAUDE.md "background audio must use the native audio path, not pure Web Audio... Pure Web Audio suspends when the screen locks on iOS"):** InnerEase already has a hard rule that its relief audio must survive lock screen via the native path. What is MISSING from every fleet app's stack today is lock-screen PLAYBACK CONTROLS (play/pause/skip on the lock screen and Control Center), which is table stakes for any meditation/relief-audio competitor (Calm, Headspace, Balance) and currently absent fleet-wide. This is a genuine premium-feel GAP: InnerEase's audio can survive the lock screen per its own rule, but the user cannot control it from the lock screen without unlocking the phone, which undercuts the "wellness app" premium polish bar. Call: adopt-now for InnerEase specifically (once Phase 0 lands), it is cheap and directly closes a competitive-parity gap against every meditation-app peer. Effort: S.
- **AWARE (training exercises, potentially longer audio sessions):** same lock-screen-controls gap; lower priority than InnerEase since AWARE's sessions are shorter/more interactive (tile-grid based) rather than long-form ambient audio.
- **Companion (cloned narration, family feed audio/video):** if a family member's cloned-voice narration plays for an extended story/caption read-aloud, lock-screen controls let the senior user pause without picking up the phone, matching Companion's own senior-first UX bar (large touch targets etc. extended to the lock screen). Call: adopt-later. Effort: S.

## 6. Mute (`@capgo/capacitor-mute`)

iOS. Detects the physical ring/silent switch state.

- **iHEARtest, HARD CORRECTNESS/SAFETY FINDING:** iHEARtest is a hearing SCREENING app. If the device's physical silent switch is engaged during a test, depending on how the test audio is routed, the test could play at reduced or zero perceived volume without the app knowing, producing a false or invalid screening result that the user has no way to know is invalid. iHEARtest's CLAUDE.md does not currently mention any silent-switch check anywhere in its compliance/testing rules, and this plugin is the direct, purpose-built fix: detect the switch state BEFORE or DURING a test and warn/block if it is engaged. This is not a nice-to-have, it is a correctness gap in a screening tool whose entire value proposition is producing a trustworthy result. Call: adopt-now. Effort: S. This is one of the highest-leverage single findings in this whole slice precisely because it is cheap and closes a real safety/trust gap in the flagship app.
- **AWARE (training exercises):** same class of issue at lower stakes (a silent training session is a bad-UX / wasted-session problem, not a false-clinical-result problem, since AWARE explicitly never diagnoses). Call: adopt-later. Effort: S.
- **InnerEase (relief sound sessions):** a silent relief session defeats the entire feature; same logic as AWARE. Call: adopt-later. Effort: S.
- **Companion, Flatstick, FourVault, Fictionary, PlantID:** lower relevance (none of these apps depend on audio playback volume for correctness of a measured result).

## 7. Incoming Call Kit (`@capgo/capacitor-incoming-call-kit`)

iOS CallKit native incoming-call UI, Android full-screen notification equivalent.

- **Companion, MISSED OPPORTUNITY, non-obvious and high-value:** Companion's entire pitch rests on scam detection and trust for a 70+ user. Today, if the fleet's existing Twilio/ElevenLabs voice-agent automation (or a future human-escalation feature) needed to reach a senior user by voice, the natural path is a regular PSTN phone call through Twilio, which arrives as an UNBRANDED, unknown-number call. For an app whose entire job is teaching seniors to distrust unexpected calls, an unbranded incoming call FROM THE APP'S OWN SAFETY NET looks exactly like the threat the app exists to prevent. This is a genuine, non-obvious product risk hiding inside an obvious feature idea (call the senior for help). This plugin closes that gap: a native, branded, full-screen "OTCHealth Companion" incoming-call UI (via CallKit, paired with Twilio Voice below) is immediately, visibly trustworthy in a way a bare phone number never can be. Call: adopt-later (spike first to confirm CallKit works well within Companion's existing entitlement/RevenueCat gating). Effort: M.
- **B2B / Medvi-style angle:** a "verified branded call" capability is directly sellable as a B2B feature to senior-care facilities and to AWARE's own audiologist-clinic B2B licensing line (a clinic could trigger a branded in-app call to a patient for an appointment reminder or a follow-up, which is both more trustworthy AND more HIPAA-conscious than an ordinary SMS/call since it is app-mediated). This is a genuine new B2B product surface, not currently proposed anywhere in the fleet's docs. Call: spike. Effort: M.
- **iHEARtest / AWARE (escalate a failed or borderline hearing screen to a real hearing professional, the "Mark review ritual" ethos extended to the end user):** the same branded-call trust logic applies to a "talk to a hearing professional now" escalation button. Call: spike. Effort: M.

## 8. Twilio Voice (`@capgo/capacitor-twilio-voice`)

VoIP calling (make/receive) via Twilio Voice SDK, native audio/camera/room lifecycle bridged into Capacitor.

- **Pairs directly with Incoming Call Kit (item 7) as the underlying calling transport.** Architecturally distinct from the fleet's EXISTING server-side Twilio/ElevenLabs voice-agent automation (which almost certainly rings the user's normal phone number via PSTN today, independent of whether any app is installed). Adding this plugin is additive, not a replacement: it lets a call originate or land INSIDE the app itself with native call UI, rather than as an ordinary phone call. Call: adopt-later, bundled with the Incoming Call Kit spike above. Effort: M.
- **MedReview, FLAG:** if a future medication-reminder or pharmacist-callback feature used this for PHI-adjacent conversation, the call audio/transcription path would need the same BAA-ring scrutiny as any other PHI surface; Twilio is explicitly listed in MedReview's own CLAUDE.md as "payment-only under HITECH Section 1179, allowlist at packages/api/src/services/stripe.ts" implying Twilio itself is NOT currently BAA-scoped for MedReview. Call: skip for MedReview until/unless Twilio is added to the BAA ring for voice specifically. Effort: S (verification only).

## 9. Twilio Video / RealtimeKit (Cloudflare Calls) — `@capgo/capacitor-twilio-video`, `@capgo/capacitor-realtimekit`

Both provide native video calling; RealtimeKit ships with built-in UI for video meetings, Twilio Video gives native audio/camera/room lifecycle events with more DIY control.

- **Companion, THE BIGGEST MISSED OPPORTUNITY IN THIS SLICE:** Companion's Pillar 2 (family layer) today is explicitly ASYNC ONLY per its own CLAUDE.md ("a private, invite-only family photo and video feed... Async only in v1" for the voice-cloning pillar, and the family layer itself is framed as feed-plus-check-in, not live video). The entire pitch line is "one less call to the adult child." A LIVE, senior-friendly, large-button video call embedded directly in the app (not a redirect to FaceTime/Zoom, which are exactly the kind of confusing-screen problem Pillar 1 exists to solve for this same user) turns the product from "the app that helps with photos and scam alerts" into "the easiest way to see your grandkids," which is a fundamentally stickier daily-use hook and a much stronger justification for the Family ($24.99/mo) and Legacy ($39.99/mo) tiers that currently differentiate mainly on clone count. This is a genuinely new premium surface, not a gap-fill, and it directly serves the buyer (the adult child) who wants an easy way to check in on a parent visually. Call: spike now, adopt-later as a real roadmap item (this is a Week 3+/V2 scope decision, not a quick add, given RevenueCat entitlement wiring and PostHog sensitive-surface tagging both need to extend to a live video surface, e.g., a NEW `ph-no-capture` class for the call UI). Effort: L.
- **RealtimeKit vs Twilio Video comparison for this use case:** RealtimeKit's built-in meeting UI is a faster path to a working senior-friendly interface (less custom UI to build and accessibility-audit against Companion's WCAG AAA / 64x64pt touch-target bar); Twilio Video gives more control if Companion wants a fully custom, senior-optimized calling screen (large single "answer" button, no meeting-app chrome). Recommend spiking RealtimeKit first for speed, Twilio Video as the fallback if its UI cannot be made senior-appropriate without a full custom build. Effort note applies to whichever is chosen, not both.
- **AWARE / InnerEase / MedReview:** no direct fit (no family/caregiver video-call feature described in any of their docs).

## 10. LLM (`@capgo/capacitor-llm`)

iOS, Android. On-device inference: iOS backend is Apple Intelligence (system model) or bundled MediaPipe model files; Android backend is MediaPipe model files. Methods: `createChat`, `sendMessage`, `getReadiness`, `setModel`.

- **InnerEase, STRONG ARCHITECTURAL FIT, WITH A COMPLIANCE TRAP:** InnerEase's non-negotiable rule 5 (on-device-first, no backend, no PHI, no BAA in V1) makes an on-device LLM structurally the RIGHT shape for delivering CBT/ACT exercise content and conversational prompts without a cloud round-trip. Paired with Speech Recognition (item 1) and Speech Synthesis (item 2), this could form a fully local voice-driven wellness loop. HOWEVER, InnerEase's non-negotiable rule 6 is explicit and unconditional: "Clinical content (CBT and ACT) is drafted with assistance but requires clinical sign-off before it ships... this sign-off decision routes to Matt directly." Running the CBT/ACT content generation ON-DEVICE does NOT waive that sign-off requirement; the risk is a future engineer treating "it is just a local model, not a cloud call" as equivalent to "it does not need clinical review," which it does not. Flagging this explicitly as an anti-pattern TRAP to avoid, not a reason to skip the plugin itself. Call: spike (the plugin), with the sign-off rule restated in the same PR/spec that adopts it. Effort: M.
- **Companion, cost-reduction angle:** a coarse on-device pre-classifier ("is this mail piece scam-shaped, yes/no/uncertain") ahead of escalating to the heavier cloud Gemini 2.5 Flash / Live pipeline mirrors the fleet's own model-routing pattern (Fleet Intelligence #5, gpt-4o primary / gpt-4.1-mini fallback in company-brain) but ON-DEVICE rather than cross-cloud, which is a further cost and latency win beyond even a cheaper cloud model. Call: adopt-later (spike after Speech Recognition item 1 lands, since both feed the same "reduce Gemini Live/Vertex call volume" goal). Effort: M.
- **Apple-Intelligence dogfood note (fleet-wide, per otchealth-claude-tools CLAUDE.md, "the dogfood device for on-device LLM features"):** this plugin IS the literal Capacitor bridge to that already-named dogfood target. No app currently uses it; it is the concrete implementation vehicle for a fleet ambition that is currently just a stated intention with no code behind it.

1. **Companion live family video calling (RealtimeKit or Twilio Video).** Companion's family layer today is async-only (photo/video feed, daily check-in). A native, senior-friendly, large-button LIVE video call embedded directly in the app is a fundamentally stickier daily-use hook than an async feed and directly strengthens the case for the higher-priced Family/Legacy tiers. This is the single biggest net-new-surface idea in the slice, not a gap-fill of an existing plan.

2. **Branded native in-app calling (Incoming Call Kit + Twilio Voice) for scam-response escalation and B2B "verified call" packages.** Solves a real, non-obvious trust problem specific to Companion's positioning: an unbranded incoming phone call from the app's own safety net looks exactly like the threat the app exists to prevent. Branded CallKit UI fixes that, and the same "verified branded call" capability is directly sellable to senior-care facilities and AWARE's audiologist B2B line as a Medvi-style differentiated feature.

3. **On-device Speech Recognition (plus a future on-device LLM pre-filter) as a cost lever on Companion's hard-capped, metered Gemini Live minutes.** This is a direct COGS reduction on a usage-metered, revenue-gating resource, i.e., a billion-dollar-company-relevant unit-economics lever, not just an accessibility nicety, though it also directly satisfies Companion's own "every action reachable by voice" rule.

## Anti-patterns / hard-constraint conflicts

- **Speech Recognition and MedReview PHI:** the plugin's underlying platform speech engine (Apple/Google) may phone home to a non-BAA cloud for cloud-backed recognition even when the app itself never intended that. Adopting this plugin naively on a future MedReview Capacitor build without first confirming and enforcing on-device-only recognition would silently route PHI-adjacent speech (medication names, symptoms) outside the BAA ring, a direct violation of MedReview's own hard PHI-architecture rules. Verify before any use, same posture the main report already flags for the Health plugin.
- **On-device LLM (InnerEase) as a false compliance shortcut:** running CBT/ACT content generation locally on-device does not waive InnerEase's non-negotiable rule 6 (clinical sign-off required before any clinical content ships). The trap is treating "no cloud call" as equivalent to "no compliance review needed." They are unrelated axes.
- **Twilio Voice for MedReview PHI-adjacent calls:** MedReview's CLAUDE.md currently scopes Twilio as payment-only/non-existent in its BAA ring notes (Twilio is not named as a BAA-covered service at all in MedReview's docs, only Stripe is called out under HITECH 1179 for payment). Any future voice feature carrying PHI-adjacent conversation content must not assume Twilio is already BAA-covered; it is not, per the current docs.
- **Native plugin adoption vs Capgo OTA scope, general reminder for this whole slice:** every plugin in this report that touches native audio session behavior, VoIP/CallKit, or bundles an on-device model (Audio Session, Incoming Call Kit, Twilio Voice/Video, RealtimeKit, LLM) is NATIVE code, not a web-layer change. Per the main Capgo platform-docs research, `@capgo/capacitor-updater` (the fleet's OTA engine) only ships JS/HTML/CSS/web-asset changes over the air; any of the plugins recommended above requires a real binary release through Depot macOS CI, not a silent OTA push. This is a scheduling/release-planning constraint on every "adopt-now" item above, not a reason to avoid them, just a reminder they ride the normal App Store review cadence, not the fast OTA channel.
- **MedReview + Capacitor-only plugins in a non-Capacitor V1:** Speech Synthesis (and by extension any Capgo plugin) is unnecessary overhead for MedReview's current pure React SPA V1 (no Capacitor runtime at all until V1.1). Pulling in a Capacitor plugin purely for its web shim, when the standard browser API achieves the same result with zero added dependency, is over-engineering for the current phase.

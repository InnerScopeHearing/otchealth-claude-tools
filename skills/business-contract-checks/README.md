# Business contract draft checks

Deterministic validators for internal drafts using bounded metadata only; they never retrieve or inspect source bodies. This package supports draft validation for N08 entitlement, N09 stock/payment/customer-promise/fulfillment freshness, and N10 supplier-handoff records. Every result is labeled `draft_validation` with `live_authorization: false`; `ready` means only that supplied draft metadata satisfies the contract. It does not establish customer eligibility, authorize purchases, submit supplier commitments, create orders/refunds, contact people, or adopt a medical/legal/commercial policy.

Run `node cli.mjs < fixture.json` from this directory. The CLI reads one JSON object from stdin, for N08/N10 accepts synthetic marker strings, timestamps, enumerated metadata and numeric/boolean values; for N09 accepts bounded opaque metadata identifiers, timestamps, enumerated states and numeric/boolean values; rejects free-text and customer-identifying/body fields, emits diagnostics only, and performs no network or filesystem writes. Top-level input must include `draft_validation: true`, `live_authorization: false`, and `workflow: "N08"`, `"N09"`, or `"N10"`. N08 fields: `purchase`, `packs`, optional `follow_up`, `context`, `now`. N10 fields: `handoff`, `context`, `now`. N09 fields: `stock`, `payment`, `promise`, `fulfillment`, and `context`. N09 requires caller-supplied `context.now`, explicit `freshness_thresholds_ms.stock` and `.payment`, scope, current source versions, current promise version, and immutable native records. Each stock/payment/promise/capacity source must exactly match one unique immutable record, current source version, and requested SKU/location/channel scope. Missing or stale stock, unconfirmed/disputed payment, promise-version drift, insufficient/missing capacity, and fulfillment exceptions hold. Exceptions require a caller-accepted owner, future due time, and native reference; even a fully owned open exception remains held. N09 outputs structured `reason_codes` and remains draft-only; `ready` never authorizes an order, payment, customer promise, or fulfillment action.

Workflow: `node cli.mjs commerce < pass-n09.json` from this directory. The included fixture shows the N09 input shape; replace its opaque pointers and caller-owned thresholds with draft adapter output before validation. The CLI remains local, read-only, and diagnostic.

Tests: `node --test *.test.mjs`. Tests use synthetic fixtures and no provider or service calls.

# N11 marketing draft workflow

Deterministic, metadata-only draft validators. N08/N10 accept synthetic fixtures; N11 also accepts bounded opaque native metadata IDs and version links so an adapter can preserve real provenance pointers without reading source bodies. N11 rejects free text and identifying/content fields. Every result is labeled `draft_validation` with `live_authorization: false`; marketing activation is always `disabled`. A `ready` result means supplied metadata satisfies this draft contract only. It does not authorize activation, audience selection, batch marketing, care communications, or sending and does not establish any marketing policy.

Run N11 as a workflow adapter from this directory:

```sh
node cli.mjs marketing < marketing-pass.json
```

The CLI reads one JSON object from stdin, emits a JSON result only, and performs no network or filesystem writes. Top-level input must include `draft_validation: true`, `live_authorization: false`, and a supported `workflow`. N11 requires `marketing_draft`, `context`, and strict UTC/offset `now`; its fixture schema shows the exact object shape. `marketing_draft.purpose` must be `marketing`, so care workflows remain outside this adapter. Consent must be active and match the draft channel and each caller-supplied `context.scope_keys` dimension within the current effective/expiry window. Each used claim must have explicit approved metadata and match the current source ID/version. Review acknowledgment must name a role from caller-supplied `context.required_reviewer_roles`, match the exact draft version, and carry reviewer, native receipt, and outcome references. Missing inputs, stale/revoked/expired consent, claim or source mismatch, and missing/stale reviewer acknowledgment hold. The validator does not fetch or infer current policy: the internal adapter must supply its current approved-claim, source-version, scope, and reviewer metadata with native provenance references.

N11 allows bounded opaque identifier/version/link strings up to 256 characters with no whitespace; it rejects names, email/phone/address, customer/patient/order fields, and body/content/message/prompt/copy fields. Do not include draft copy or source text. N08 and N10 retain their synthetic-marker-only input rules. N08 fields: `purchase`, `packs`, optional `follow_up`, `context`, `now`. N10 fields: `handoff`, `context`, `now`.

Tests: `node --test *.test.mjs`. Tests use synthetic fixtures and opaque pointer examples only; no provider or service calls occur.

N09 also requires caller-supplied `accepted_payment_states` and immutable native record `facts`: stock/capacity available_quantity, payment status/payment_ref, and promise version. Claimed values must exactly match these supplied facts. N11 `required_reviewer_roles` is the caller-approved role allowlist for one acknowledgment; this adapter does not decide how many reviews policy requires. All N09/N11 outputs disable activation, including malformed metadata and hold outcomes.

# Chat and Codex acceptance

Use this procedure when renewing skills/plugins or verifying their adoption in Chat and Codex. Apply it to a finite list of relevant plugins and exact target sessions. Skill instructions can load without vendor tools; executable vendor integrations need their own dependencies and company connection.

For each row record the intended seat, product (ordinary Chat, Work, local Codex or Codex Cloud), exact session/project/environment identifiers when exposed, plugin ID, publisher release, loaded package URI, source hash, tested operation, receipt IDs and unresolved dependency. Unknown identifiers remain unknown. Start with existing own-seat grounding; do not read another role's Brain to fill a gap.

Resolve installed skills through the actual native skill catalog and its exact package/resource URIs. If a short alias fails, use the catalog-provided full identifier once. Read the main instructions and a supporting resource required for the task. An absent file on another filesystem does not prove the native resource is missing. Compare raw content only under the documented encoding/newline contract; report canonicalized text separately from exact byte identity.

| Stage | Required evidence | Insufficient evidence |
| --- | --- | --- |
| Published | Guarded release receipt and independently retrieved expected source | ZIP creation or source branch |
| Installed | Exact target's product install metadata | Another session's directory listing |
| Discoverable | Target skill catalog resolves expected package | Publisher says latest |
| Loaded | Target reader returns that version's main instructions and required resources | Filesystem presence |
| Exercised | Target applies loaded instructions to a bounded harmless case | Structural lint alone |
| Vendor Read | Actual authorized operation against intended company connection | Server URL or tool name |
| Vendor Write | Controlled authorized write, exact readback and restoration as applicable | HTTP success or dry run |
| Scoped Admin | Separately bounded administration proof for that caller | Read or synthetic Write |

Use a harmless instruction-only exercise first: a successful Work invocation is offered as ordinary-Chat proof; a publisher release differs from the actual cache; a required runtime interface is absent; or a denied action is proposed through another route. The correct result preserves the tested surface/version and reports the exact missing dependency. This accepts instruction behavior only. Real provider access needs its own permitted probe.

When a required direct tool fails or is missing in ordinary Chat, follow the applicable project rule: the matching app's supported Settings Refresh once, then catalog readback in that same Chat. If the control is unavailable, preserve the reviewed source and report the missing refresh/binding control. Do not reconnect, swap roles, manufacture an endpoint, or change approval/security policy to work around a rejection. A source update can fix an owned packaging defect; it cannot grant the host a missing runtime interface.

For repository Codex, put the exact skills under the actual authorized checkout's supported discovery layout. For cloud targets, verify the committed layout, named environment and running checkout, then directly load there. A toolkit subfolder, feature branch or laptop copy is not proof that a cloud loader sees it. Prefer the private account plugin on supported Chat/Work clients. Keep ordinary Chat and Codex rows separate even when they share an account.

Record one result for each row: accepted at the precise tested level, blocked with the dependency, unverified without sufficient observation, or unknown for an uncertain mutation. Reconcile unknown writes before retrying. An all-target claim requires all required rows to pass; enumerate excluded and inaccessible targets explicitly. Finish independent viable rows when one target is blocked.

Preserve the previous release, expected-release guard, source commit and available supported rollback operation. Updating a plugin does not establish hot reload, vendor health, or rollback execution. Keep the receipt in durable source-owned evidence and save a minimal own-seat checkpoint with exact readback.
